## Learn:
1.支付订单的幂等性：
存在网络波动、失败重试等情况，导致的同一订单发起了多次请求，在支付场景下，容易导致后台记账混乱，用户体验困惑。
因此，前端采用防抖 + 生成全局唯一id，保证同一订单的多次请求，id全局唯一。
哪怕存在多次请求，后端采用分布式锁 + 去重表，保证只消费一次。
    Redis 分布式锁，key 为 pay:订单号，防止并发穿透。
    拿到锁后，在 ID 为唯一索引的幂等表中，查询该 ID 是否存在。
    在同一事务中，执行插入幂等记录、执行扣款、更新订单状态，保证原子性。
乐观锁维护好状态机，涉及订单状态变更时，更新 sql，一定要带上旧状态为条件，防止已支付的订单再次扣款。
微信/支付宝的三方异步回调，可能因网络超时多次发送同样的回调报文，用三方的 transaction_id + 商户订单号 作为幂等键，先查本地订单状态，再决定是否要处理业务。
